# star-model

Reproducible dataset, benchmark, and evolutionary fine-tuning pipeline for StarIntel models.

`star-model` builds the corpus. **`llm.starintel.actor` is the training controller**: it receives a dataset manifest, selects a configured cheap inference provider for synthesis, provisions a GPU training backend, launches fine-tuning, records status/checkpoints, and publishes the resulting model artifact.

## Corpus families

- Public StarIntel code repositories, split into task-shaped examples instead of raw repository dumps.
- Public Prolog code and Prolog reasoning/completion tasks.
- Synthetic StarIntel Prolog facts, schemas, rules, queries, migrations, and repairs.
- Synthetic StarIntel JSON / JSON-LD documents and transformations.
- Synthetic tool-calling conversations generated by a stronger teacher model.
- Synthetic ingest jobs and failure/recovery cases.
- Synthetic database/data-model migrations.
- Synthetic OSINT and StarIntel tool design and safe implementation tasks.
- Synthetic independent-research tasks that require grounded evidence and provenance.
- Synthetic document-generation tasks with machine-checkable output requirements.
- Synthetic actor-system generation tasks with runnable tests.

Every record carries source, license/provenance, generator/model, task family, content hash, and split metadata. Generated data must never contain secrets or private repository content.

## Dataset flow

```text
public repos --> harvest --> normalize --> taskify --+
Prolog corpora ------------------------------->     |
                                                      +--> validate --> dedupe --> mix --> manifest
llm.starintel.actor --> synthetic generators ------> |
                                                      +--> fine-tune request --> llm.starintel.actor
                                                                                  |
                                                                                  +--> GPU backend
                                                                                  +--> checkpoints
                                                                                  +--> model artifact
```

See `config/dataset.toml`, `schema/example.schema.json`, and `.github/workflows/dataset.yml`.

## Evolutionary fine-tuning

The evolution harness treats a fine-tuned adapter as a candidate. A candidate genome contains:

- the training-corpus mixture;
- QLoRA learning rate, rank, alpha, dropout, warmup, and related training settings;
- optional lightweight tool-router settings.

A generation is benchmarked on held-out tasks and then selected using a Pareto frontier. The main fitness signal is **accepted useful artifacts**, not eloquence or token count. The default priority is:

1. independently completed, grounded research artifacts;
2. valid generated documents;
3. runnable actor systems whose tests pass;
4. correct tool calls;
5. successful ingest jobs.

Research artifacts do not count unless they are marked grounded and independently completed. Actor systems do not count unless their validation/tests pass. A configurable quality floor prevents a candidate from winning by emitting large quantities of junk.

The evolutionary loop is intentionally split from the expensive training backend:

```text
seed genomes
    |
    v
fine-tune requests ---> llm.starintel.actor ---> adapters/checkpoints
    |                                             |
    +---------------------------------------------+
                                                  v
held-out benchmark traces ---> quality gates ---> score
                                                  |
                                                  v
                                         Pareto selection
                                                  |
                                      +-----------+-----------+
                                      |                       |
                                  keep elites             mutate genomes
                                      |                       |
                                      +-----------+-----------+
                                                  |
                                                  v
                                           next generation
```

Failure traces can be converted into a stronger-teacher synthesis request. That gives the loop a GEPA-like reflection step without letting the teacher directly choose the winner: held-out benchmark results still decide selection.

### CLI

Create generation zero:

```sh
python scripts/evolve_finetune.py seed \
  --output-dir evolution/g000
```

Build candidate fine-tune requests:

```sh
python scripts/evolve_finetune.py requests \
  --candidate-dir evolution/g000 \
  --manifest dataset/manifest.json \
  --base-model "$STAR_BASE_MODEL" \
  --output-dir evolution/g000/requests
```

Submit them through `llm.starintel.actor`:

```sh
python scripts/evolve_finetune.py submit \
  --request-dir evolution/g000/requests \
  --actor-url "$STAR_LLM_ACTOR_URL" \
  --output-dir evolution/g000/submissions
```

Score held-out JSONL traces and make the next generation:

```sh
python scripts/evolve_finetune.py score \
  --results evolution/g000/benchmark.jsonl \
  --output evolution/g000/scores.json

python scripts/evolve_finetune.py evolve \
  --candidate-dir evolution/g000 \
  --scores evolution/g000/scores.json \
  --output-dir evolution/g001
```

Turn failures into targeted teacher data:

```sh
python scripts/evolve_finetune.py reflect-request \
  --results evolution/g000/benchmark.jsonl \
  --output evolution/g000/repair-synthesis.json
```

Archive generation scores through StarIntel's canonical bulk ingest API:

```sh
python scripts/evolve_finetune.py ingest-scores \
  --scores evolution/g000/scores.json \
  --starintel-url "$STARINTEL_URL"
```

The archive envelope version is configurable because the deployed StarIntel server and the corpus spec may move at different times.

## Lightweight neural tool router

`scripts/train_tool_router.py` is an optional tiny PyTorch MLP. It hashes input tokens into a fixed feature vector and predicts a tool label. This provides a cheap baseline for tool selection and can also act as a first-stage router before the generative model.

```sh
python scripts/train_tool_router.py train \
  --input data/tool-routing.jsonl \
  --output models/tool-router.pt
```

Rows are simple:

```json
{"input":"research the public DNS history for this domain","tool":"domain_research"}
```

The router's held-out accuracy can be fed into the same evolution benchmark as a tool-calling signal.

See `config/evolution.toml` and `schema/benchmark-trace.schema.json` for the full benchmark contract.
